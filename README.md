# symphony-start

The front door to the Symphony template: install the App, press Create on the form it sends you to, and a pull request lands in your repository within about two minutes with the template, or only its claim protocol, filled in with your names. The template's repository stays private; the files in the pull request are yours.

## Adopt it in three steps

1. **Install the App** on the repository: https://github.com/apps/symphony-dev/installations/new, "Only select repositories", that one. It needs a commit (a README is enough) and you must administer it. For the repository's settings too (the default branch's ruleset, delete-on-merge and auto-merge, secret scanning with push protection), install the **Setup App** on it as well, https://github.com/apps/symphony-setup/installations/new, again "Only select repositories": it holds Administration for the one run and uninstalls itself when the run is done, when that repository was the only one it reached. Either install ends on the form, and the form's first line links the other.
2. **Press Create** on the form. The kind is read from the repository (an empty one gets the whole template, one with files the protocol alone), anonymous aggregates are shared, and a pull request opens in every repository the installation reaches that has no adoption yet and that you administer. The Kind dropdown overrides the reading; one box has the run merge the pull requests for you; one turns sharing off. The form is also open on its own, https://github.com/OpenSpineConsortium/symphony-start/issues/new?template=adopt.yml, where you name the repository instead.
3. **Review and merge the pull request** that opens in your repository, from the branch symphony/adopt, within about two minutes, unless you had the run merge it. The issue here is answered and closed; it names your repository only when you typed the name.

Or skip the form: installing the App is a request too. Every ten minutes a sweep here (.github/workflows/sweep.yml) finds the repositories the App reaches that have no adoption yet and opens the pull request in each, reading the kind from the repository itself: a default branch holding nothing but what GitHub makes when it initializes a repository (a README, a LICENSE or COPYING, a .gitignore or .gitattributes) is a new repository and gets the whole template; anything else is an existing repository and gets the protocol alone. The pull request says which it read and how to get the other kind. Sharing of anonymous aggregates is on, as the form's default, with the same switch. The form wins where both are in play: an installation younger than half an hour is left alone, so filling in the form right after installing keeps your choices, and a repository named on an open request here is left to that request. The sweep passes over, silently, an installation that has not accepted every permission the pull request needs (an owner accepts a pending one on the page of installed GitHub Apps), a repository whose Issues are off (the run tells the repository in an issue when it could not open the pull request), one that already has the branch symphony/adopt or the protocol, one whose pull request from symphony/adopt was closed without a merge (declining it once is declining it; the form still works), and one that opted out: a repository that wants the App without an adoption, for the metrics alone, writes `off` in `.github/symphony-adopt` on its default branch. When the run the sweep started could not open the pull request, the App opens one issue in the repository saying why, and the sweep waits while it is open: close it once the cause is gone and the next sweep tries again. The form stays the faster way, answered within a minute, and the way to choose the kind and the metrics yourself.

The run makes the board's labels in your repository at once, pushes the branch symphony/adopt, applies the settings where the Setup App is installed and, for a new repository, opens the issue "Set up this project" there; everything else lands only when you merge. You can close the pull request instead, which leaves those labels, that branch, those settings and that issue for you to delete, undo or close. Uninstalling the App afterwards undoes nothing in your repository; it only stops the metrics below from being read. Uninstalling the Setup App is what you do once the pull request is open.

## What each kind adds

**New repository: the whole template**, as "Use this template" would make it: the instructions and rules every Claude Code session reads (CLAUDE.md, .claude/), the shared memory, the board and its workflows, the checks, team mode's workflows, the setup scripts and the documents, with the placeholders filled with your repository's names, the template's marker folder removed and a blank session checkpoint. The template's own init does the filling, so the copy is the one GitHub would have made. A file your repository has already that the template also has, typically the README GitHub made, is replaced, and the pull request lists it; files the template does not have are left alone. The run also makes the board's labels and opens the issue "Set up this project" in the repository, as the template's own init does after "Use this template", since the copy's README and its setup pages send you to that issue; when it cannot be opened, the answer here says so, and the pull request's next steps and docs/setup/owner-checklist.md stand in for it. With the Setup App installed, the run sets up the GitHub side at once, as `bash scripts/setup-repo.sh` would from a clone; without it, that script does afterwards (or `python3 scripts/crowd.py setup` for a project worked by volunteers on their own Claude accounts), and the pull request says which.

**Existing repository: the protocol only**, the files a person would otherwise copy by hand, so the template's tests, checks and documents never meet yours:

- tools/sdlc_protocol/ and tools/VENDORED, the claim protocol's library as the template vendors it, with tools/board.py;
- .github/workflows/board.yml, which keeps the board on the branch `board`, and .github/workflows/tidy.yml, which deletes a closed issue's claim branch;
- docs/agents/PROTOCOL.md, the protocol in prose, which is the public symphony-protocol's own spec/PROTOCOL.md at the release the template vendors, and docs/agents/claims/README.md;
- a section "How work is claimed" at the end of your CLAUDE.md (or a new CLAUDE.md with it), which imports the protocol into every session;
- two keys in .claude/settings.json, `extraKnownMarketplaces` and `enabledPlugins`, which name OpenSpineConsortium/symphony-marketplace and enable its plugin symphony (the skills, /symphony:board and the push guard); every key your file has stays, and a file that is not valid JSON is left alone and the pull request says so;
- the board's labels, made by the run at once.

No file of yours is overwritten: one that is there already is kept and listed as kept. What is left by hand, each person installing the plugin once and, without the Setup App, protecting the default branch, is in the pull request.

Both kinds write `.github/symphony-metrics`, the metrics switch below, and bring the template's metrics workflow once the template carries it. Neither copies LICENSE: licensing your project is your decision; the files themselves are offered under the MIT License, whose text is this repository's LICENSE.

**The settings, with the Setup App.** Where you installed the Setup App on the repository, the same run applies what the template's `scripts/setup-repo.sh` applies from a clone: the ruleset of the template's docs/setup/ruleset-main.json on the default branch (a pull request required, force pushes and deletions blocked, and in a new repository the check named "check" required, which the pull request itself runs; an existing repository's ruleset requires no check, since the template's CI job is not there, and the pull request says to add your own check's name to it), "Automatically delete head branches" and "Allow auto-merge", and secret scanning with push protection where the plan and the visibility offer them. A ruleset of that name the repository has already is left as it is. The pull request's section Settings says what was done and what GitHub refused, in GitHub's own words, and the next steps follow from it; the run's public log says only, per setting, whether it was done. Where no token for the repository can be made, the pull request says the App is not installed on it, or, when a probe on the owner's own installation fails too, that the front door's Setup App is not working; the run then tells the owner in an issue here, opened once and commented on after, since a red run would be reported only to the requester. A run that stops after the token was made says on the request that the settings may already be applied. The labels are made with the main App's token, as before; no variable is set and no secret is ever asked for: a Claude token is yours, set with /install-github-app in Claude Code. Then uninstall the Setup App: it holds Administration on your repository and nothing else uses it.

## What is shared, and how to turn it off

By default a repository that adopts the template shares anonymous aggregates of the protocol at work, so it can be measured in real projects: counts (claims, pull requests opened, merged and closed, reviews, check runs passed and failed, conflicts, released claims, contributors as a number), durations (medians and 90th percentiles from claim to pull request, from opening to merge, to the first review), rates (merge rate, first-check pass rate) and, when a maintainer runs the judge, failure-type frequencies. Never code, text, titles, logins, branch names or repository names. Your repository's own workflow computes the counts, the durations and the rates and writes them to the file METRICS.json on its branch `metrics`. Failure-type frequencies come only from JUDGE.json on that branch, which exists only when a maintainer runs the judge (`python3 tools/metrics.py judge`) on their own machine and their own Claude account, and which holds category counts and nothing else. The App reads METRICS.json and JUDGE.json on the branch `metrics` and nothing else, and the dataset names your repository only by a salted hash. That workflow comes with the template; until the template carries it, an adoption records the switch and nothing is computed or shared.

To turn it off, at any time: choose "Do not share" in the form; or write `off` in `.github/symphony-metrics` on your default branch; or set the repository variable SDLC_METRICS to `off`. Uninstalling the App stops it too. While it is off, the workflow writes only that sharing is off.

## The template stays private

OpenSpineConsortium/symphony-template is internal to its enterprise, and adopting it does not change that. The App reads it inside this repository's workflow, with a read-only token that is revoked as soon as the files are read, and writes them into a pull request in your repository.

What that means: the files in the pull request are yours to read, change and keep, in a private repository or a public one, and nothing about them is hidden from you. What it does not mean: access to the template's repository itself, its history, its issues, its pull requests or its other branches, none of which leave the run; and no later change reaches your repository by itself. Later releases of the protocol come from the public OpenSpineConsortium/symphony-protocol, by its scripts/vendor.py and a pull request of your own, as the pull request's last lines say.

This repository is public, and so is everything on its issues: a repository name you type in the form, and the workflow run that handles it, are visible to anyone. If a private repository's name says more than you want to show, keep the issue's title a throwaway description, and come to the form from the install, which fills in the installation's number and no name: the run resolves the name for itself with the App's own token, masks it, and answers "your repository"; the number says nothing to anyone but the App. Until a request passes the run's checks, its log shows only whether the account you name has installed the App, and nothing about the repository itself: a repository the App does not reach and an author who is not one of its administrators get the same answer; a form carrying an installation that is not the App's, or one that reaches several repositories, or whose author is not an administrator of the one it reaches, gets one answer too. A request that passes shows what the run did there, as any run does, which is the name of your default branch, the labels it made and, per setting, whether the Setup App applied it; the files it staged, git's own messages, GitHub's answers about the settings, the names of your other branches and the number of any pull request or issue in your repository are never printed. A repository the sweep found may be private and was named on no public issue, so its name never reaches the public side at all: the sweep prints counts, the run it starts is given the installation's and the repository's numeric ids, and the run resolves the name with a metadata-only token and masks it before anything else can print it.

## How it works

- .github/ISSUE_TEMPLATE/adopt.yml, the form, labels its issue `adopt`: the installation GitHub fills in, or a repository's name, the kind (Auto by default) and two boxes, merge for me and do not share.
- .github/workflows/adopt.yml runs on that issue: it reads the form, makes the App's token for the account that owns your repository and checks with it, silently, that the App reaches the repository and that the issue's author is one of its administrators, or, when the form came from the install with the installation's number and no name, runs scripts/resolve.py, which turns either App's number into every repository the installation reaches with no adoption yet that the author administers, all by id; it answers what it refuses, and then calls adopt-run.yml once with the repository's name, or once per repository with the ids, and answers an installation's request once for them all.
- .github/workflows/adopt-run.yml is the adoption itself, for both paths: it makes the token that writes there, reads the template with a read-only token, in mode existing fetches the protocol's page from the public OpenSpineConsortium/symphony-protocol at the release the template vendors, runs scripts/adopt.py on a checkout of your repository, commits on the branch symphony/adopt as the App, applies the settings with the Setup App's token where that App is installed and revokes it, opens the pull request, makes the labels and, in mode new, opens the setup issue; on the issue path it answers the issue. Its header says why each step is as it is.
- .github/workflows/sweep.yml runs every ten minutes: scripts/jwt.sh signs the App's JWT with openssl, scripts/sweep.py lists the App's installations and their repositories and keeps those with no adoption yet, within a time budget under the JWT's life and from a different installation each time, and the workflow starts adopt-run.yml for each by dispatch, with ids and never names. GitHub stops a public repository's scheduled workflows after 60 days without a commit, which the owner re-enables from the Actions tab.
- scripts/adopt.py does the reading and the copying: `parse` checks the form, `name` checks a repository's name the sweep brought, `apply` copies the files and writes a manifest of them, `body` writes the pull request's text from the manifest and the settings' report, `labels` reads the board's labels from the template's own list.
- scripts/setup.py applies the settings as the Setup App, through the REST API, and writes the report the pull request renders; `skip` writes the report that says why none was applied: no Setup App here, not installed on the repository, the front door's App broken, or a settings step that died before its report.
- scripts/refuse.sh answers a request that ends without a pull request: it says why on the issue and closes it; on the sweep's path, which has no issue, the reason is a line in the run's log and, once the run had the repository's token, the issue the App opens there, "Symphony could not open its pull request", which the sweep reads as told and skips until it is closed.

## For the owner

One-time setup, by an owner of OpenSpineConsortium, before the form works. The label comes first: GitHub applies a form's label only when the label exists, and the workflow runs only on an issue that carries it, so a request opened before the label exists starts no run, is never answered and has to be opened again once the label is there. From then on, until the variable and the secret below are set, every request is answered that the front door is not set up yet, and stays open.

1. **Make the label the form applies**:

   ```bash
   gh label create adopt --repo OpenSpineConsortium/symphony-start --color 0e8a16 --description "A request for an adoption pull request, handled by .github/workflows/adopt.yml"
   ```

2. **Make the App public**, so accounts outside the organization can install it: https://github.com/organizations/OpenSpineConsortium/settings/apps/symphony-dev/advanced, "Make public".
3. **Give the App the permission Workflows: Read and write**: https://github.com/organizations/OpenSpineConsortium/settings/apps/symphony-dev/permissions, Repository permissions, Workflows. The pull request adds files under .github/workflows/, which GitHub lets an App write only with it. The run asks the App for a token with Contents, Pull requests, Issues and Workflows as Read and write, and Metadata as Read-only, for the one repository; the App has the first three already, and Workflows is new. Every existing installation, the organization's own included, then has to accept the new permission (the installation's page shows a review request) before it takes effect; a request for a repository whose installation has not accepted it is refused with a note that says so.
4. **Check the App's installation on OpenSpineConsortium includes symphony-template**: https://github.com/organizations/OpenSpineConsortium/settings/installations, Symphony, Configure, Repository access. "All repositories" is the right choice there: it covers the template, every test repository and every copy made later. An installation's list is one list, so opening the App's install link for another repository of the organization and choosing "Only select repositories" replaces the list rather than adding to it; the front door then fails at the template's token with "Not Found" until the template is back in the list. A repository of the organization's is added under Configure, never through the install link. The App need not be installed on this repository: every answer here is posted with the workflow's own token.
5. **Give this repository the App's id and private key**, as the variable SDLC_APP_ID (https://github.com/OpenSpineConsortium/symphony-start/settings/variables/actions) and the secret SDLC_APP_PRIVATE_KEY (https://github.com/OpenSpineConsortium/symphony-start/settings/secrets/actions). From a clone, with the key file the App's settings page generated; gh reads the key from the file and nothing prints it:

   ```bash
   gh variable set SDLC_APP_ID --repo OpenSpineConsortium/symphony-start --body 5258276
   gh secret set SDLC_APP_PRIVATE_KEY --repo OpenSpineConsortium/symphony-start < symphony-dev.private-key.pem
   ```

   Anyone who can push to this repository can reach that key through a workflow, so keep write access here to the organization's owners. A key that is set but wrong, or an id that is, gets every request the answer that the front door's App is not working, leaves the issue open and ends the run red, so that it is seen here.
6. **Protect main**: require a pull request and the check named "check" (.github/workflows/ci.yml), and block force pushes and deletions, at https://github.com/OpenSpineConsortium/symphony-start/settings/rules.
7. **Register the Setup App**, from a clone of OpenSpineConsortium/symphony-app, as an owner of the organization: `python3 scripts/register.py --setup --org OpenSpineConsortium`. Its manifest (manifest-setup.json there) gives it Administration and Metadata only, no webhook, and makes it public, so anyone can install it; the script writes its credentials to .sdlc-setup-app.env on your machine and prints the next step. GitHub gives it the slug symphony-setup unless the name was taken; if it gives another, change the install link in .github/ISSUE_TEMPLATE/adopt.yml, this README and tests/test_form.py (SETUP_APP_INSTALL). Then install the Setup App on this repository, OpenSpineConsortium/symphony-start, and only it ("Only select repositories"): the workflow asks that installation for a metadata-only token when a request's mint fails, which tells an adopter who did not install the App from a wrong id or key here. A test repository of the organization's is added to that list under Configure, as in step 4, since the install link's "Only select repositories" would replace it. Until this step and the next are done, every pull request says the front door has no Setup App yet, and the steps by hand stand.
8. **Give this repository the Setup App's id and private key**, as the variable SDLC_SETUP_APP_ID and the secret SDLC_SETUP_APP_PRIVATE_KEY, with the commands the script printed:

   ```bash
   gh variable set SDLC_SETUP_APP_ID --repo OpenSpineConsortium/symphony-start --body <its id>
   python3 scripts/register.py --env-file .sdlc-setup-app.env --print-key | gh secret set SDLC_SETUP_APP_PRIVATE_KEY --repo OpenSpineConsortium/symphony-start
   ```

   The same caution as in step 5 holds, more so: this key mints tokens with Administration on every repository whose owner installed the Setup App, for the length of a run, and only for a repository whose administrator asked. The workflow mints it after its checks, revokes it as soon as the settings are applied, and holds it on no repository of the organization's but this one, whose installation it asks for metadata alone. A key that is set but wrong, or an id that is, or the installation on this repository missing, is told from an adopter who did not install the App by that probe: the pull request says the front door's Setup App is not working, and the run opens the issue "Setup App of this front door is not working" here, or comments on it while it is open.

9. **Make both installs end on the form**: on the App's settings page and on the Setup App's, under Post installation, set the Setup URL to the form, `https://github.com/OpenSpineConsortium/symphony-start/issues/new?template=adopt.yml`, and tick "Redirect on update" on both; the run reads either App's installation number. GitHub then sends whoever installs the App, or adds a repository to the installation, to the form with `installation_id` in the query string, which fills in the form's Installation field, so the person presses Create and the pull request is open within about two minutes. Without this step the person finds the form through this README, and the sweep answers an installation about half an hour later.

The files an adoption brings are offered under the MIT License, whose text is LICENSE here and which the pull request names. The adoption copies no LICENSE file into anyone's repository, since licensing your project is your decision.

## Checks

`bash scripts/check.sh` holds every file to ASCII with LF endings and a final newline and runs the tests on Python 3.12 (`PYTHON=python3 bash scripts/check.sh` takes another interpreter), and actionlint on the workflows when it is on PATH. CI runs the same script as the job named "check". The tests that run apply against the real template skip unless SDLC_TEMPLATE names a checkout of it, and CI here cannot read the template, so whoever can runs `SDLC_TEMPLATE=/path/to/symphony-template bash scripts/check.sh` before a change to scripts/adopt.py merges.
