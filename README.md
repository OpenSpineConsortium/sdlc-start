# symphony-start

The front door to the Symphony template: install the App, press Create on the form it sends you to, and a pull request lands in your repository within about two minutes with the template, or only its claim protocol, filled in with your names. The template's repository stays private; the files in the pull request are yours.

## Adopt it in three steps

1. **Install both Apps** on the repository, one install each, "Only select repositories", that one: **SymphonyBoard**, https://github.com/apps/symphonyboard/installations/new, which opens the pull request, and the **Setup App**, Symphony Setup, https://github.com/apps/symphony-setup/installations/new, which applies the repository's settings for the one run (the default branch's ruleset, delete-on-merge and auto-merge, the topic symphony, secret scanning with push protection and, for the whole template, letting GitHub Actions create and approve pull requests): it holds Administration for that run and uninstalls itself when the run is done, when that repository was the only one it reached. Installing it is your consent to the settings, so a request for a repository without it is refused, with its install link. The repository may be empty, with no commit yet: the run then makes its first commit, the README GitHub's own "Add a README file" makes. You must administer it. Installing SymphonyBoard sends you on to Symphony Setup's install page, and installing Symphony Setup sends you to the form, so the two installs are one path; the Symphony browser extension's buttons walk the same path with the repository preselected on both pages, and the form arrives with it filled in.
2. **Press Create** on the form. The kind is read from the repository (an empty one gets the whole template, one with files the protocol alone), anonymous aggregates are shared, and a pull request opens in the newest repository the installation reaches that has no adoption yet and that you administer. The Kind dropdown overrides the reading; the Merge dropdown has the run merge the pull request for you unless you choose to review it first; one box turns sharing off. The form is also open on its own, https://github.com/OpenSpineConsortium/symphony-start/issues/new?template=adopt.yml, where you name the repository instead. The form never adopts a repository twice: one whose default branch holds docs/agents/PROTOCOL.md, which every adoption from here brings, of either kind, and every copy made with "Use this template" carries, is passed over when the installation picks and refused when you name it, with one answer that names nothing of it, given before Symphony Setup is asked for, so that you are not sent to install it for a request that would be refused, since a second adoption would put the template's files over the ones it has made its own or, for the protocol alone, bring back what it has taken out. The answer says where the protocol's later releases come from instead, how to adopt it again (revert that adoption on the default branch first), what to do when that file is one of your own and how to add the topic symphony; Symphony Setup, installed for that request, uninstalls itself as it does after an adoption. A request whose adoption could not write that file, because the repository ignores it or a file or link of its own stands where it goes, is refused instead, and the answer says what to put right.
3. **Review and merge the pull request** that opens in your repository, from the branch symphony/adopt, within about two minutes, unless the run merged it for you, which it does unless you chose to review it first. The issue here is answered and closed; it names your repository only when you typed the name.

Or start from Claude Code, on your own computer: the symphony plugin's skill `/symphony:new OWNER/NAME` (https://github.com/OpenSpineConsortium/symphony-marketplace) makes the repository with gh, hands you the one link on which both Apps are installed with that repository already chosen and the form's Create pressed, waits for the pull request and its merge, and opens a cloud session on the repository with `claude --cloud`; the same steps by hand are the template's docs/start/claude-code.md, which the pull request brings.

Installing the App alone asks for nothing: the install sends you to the form, and the press is the request. A repository that wants the App without an adoption, for the metrics alone, writes `off` in `.github/symphony-adopt` on its default branch, and the form's installation path passes it over.

The run makes the board's labels in your repository at once (and, in a repository with no commit yet, its first commit: a README.md holding the repository's name, on the default branch, as GitHub's own "Add a README file" makes it), pushes the branch symphony/adopt, applies the settings and adds the topic symphony where the Setup App is installed (the sign on the repository's page that it is adopted, which the Symphony browser extension reads from the page to show "Ready for Symphony" in place of "Migrate to Symphony") and, for a new repository, opens the issue "Set up this project" there; everything else lands only when you merge. You can close the pull request instead, which leaves those labels, that README, that branch, those settings, that topic and that issue for you to delete, undo or close. Uninstalling the App afterwards undoes nothing in your repository, the topic included, which stays and is yours to remove under About; it only stops the metrics below from being read. Uninstalling the Setup App is what you do once the pull request is open.

## What each kind adds

The whole template makes the repository a Claude project: a place laid out for the teammates, with their instructions, shared memory, board, checks and setup documents, which fits an empty repository. The protocol only adds the coordination protocol for the teammates' pull requests, the claim files, the board, the rules and the hooks, to the code you already have, and replaces nothing of yours; so a repository with no commit yet is refused it, and its code goes up first. Auto reads the repository and picks.

**New repository: the whole template**, as "Use this template" would make it: the instructions and rules every Claude Code session reads (CLAUDE.md, .claude/), the shared memory, the board and its workflows, the checks, team mode's workflows, the setup scripts and the documents, with the placeholders filled with your repository's names, the template's marker folder removed and a blank session checkpoint. The template's own init does the filling, so the copy is the one GitHub would have made. A file your repository has already that the template also has, typically the README GitHub made, is replaced, and the pull request lists it; files the template does not have are left alone. The run also makes the board's labels and opens the issue "Set up this project" in the repository, as the template's own init does after "Use this template", since the copy's README and its setup pages send you to that issue; when it cannot be opened, the answer here says so, and the pull request's next steps and docs/setup/owner-checklist.md stand in for it. With the Setup App installed, the run sets up the GitHub side at once, as `bash scripts/setup-repo.sh` would from a clone; without it, that script does afterwards (or `python3 scripts/crowd.py setup` for a project worked by volunteers on their own Claude accounts), and the pull request says which.

**Existing repository: the protocol only**, the files a person would otherwise copy by hand, so the template's tests, checks and documents never meet yours:

- tools/sdlc_protocol/ and tools/VENDORED, the claim protocol's library as the template vendors it, with tools/board.py;
- .github/workflows/board.yml, which keeps the board on the branch `board`, and .github/workflows/tidy.yml, which deletes a closed issue's claim branch;
- .github/workflows/metrics.yml, which writes the anonymous aggregates described below to the branch `metrics` once a day, with the scripts it runs: tools/metrics.py and the modules of the template it imports, today tools/economics.py and tools/usage.py;
- docs/agents/PROTOCOL.md, the protocol in prose, which is the public symphony-protocol's own spec/PROTOCOL.md at the release the template vendors, and docs/agents/claims/README.md;
- a section "How work is claimed" at the end of your CLAUDE.md (or a new CLAUDE.md with it), which imports the protocol into every session;
- two keys in .claude/settings.json, `extraKnownMarketplaces` and `enabledPlugins`, which name OpenSpineConsortium/symphony-marketplace and enable its plugin symphony (the skills, /symphony:board and the push guard); every key your file has stays, and a file that is not valid JSON is left alone and the pull request says so;
- the board's labels, made by the run at once.

No file of yours is overwritten: one that is there already is kept and listed as kept. A workflow comes with every script it runs or not at all, so that it never runs a file of yours in the place of one of the template's: its own script, every module of the template that script imports, as the run reads them from the script itself, and the library, which the board's and the metrics workflow's scripts import. A file of yours where one of them goes keeps the workflow and its scripts out, unless it holds the template's own bytes, as a copy from the same release does, and so does a library of yours that differs from the template's. The metrics workflow comes only with the switch below, since it reads a missing switch as on: where the switch cannot be written, or your repository ignores it, the workflow stays out too. The pull request names the file that stood in the way. One thing this does not catch: a file of yours in tools/ named like one of Python's own modules, json.py or statistics.py for one, is what the template's scripts import in that module's place, as Python looks first in the folder of the script it runs, so rename such a file. What is left by hand, each person installing the plugin once and, without the Setup App, protecting the default branch and adding the topic symphony, is in the pull request.

Both kinds write `.github/symphony-metrics`, the metrics switch below, and bring the template's metrics workflow with every script it runs, once the template carries it. A switch of the repository's own that says off already, under that name or the one it had before the rename to Symphony, `.github/sdlc-metrics`, is never turned on: the switch the pull request writes says off too, whatever the form left, and the pull request says why. Neither copies LICENSE: licensing your project is your decision; the files themselves are offered under the MIT License, whose text is this repository's LICENSE.

**The settings, with the Setup App.** Where you installed the Setup App on the repository, the same run applies what the template's `scripts/setup-repo.sh` applies from a clone: the ruleset of the template's docs/setup/ruleset-main.json on the default branch (a pull request required, force pushes and deletions blocked, and in a new repository the check named "check" required, which the pull request itself runs; an existing repository's ruleset requires no check, since the template's CI job is not there, and the pull request says to add your own check's name to it), "Automatically delete head branches" and "Allow auto-merge", the topic symphony (the sign on the repository's page that it is adopted, shown in the About sidebar to anyone and read from the page by the Symphony browser extension, whose button then says "Ready for Symphony" in place of "Migrate to Symphony"; the topics you had stay), and secret scanning with push protection where the plan and the visibility offer them. For the whole template it also ticks "Allow GitHub Actions to create and approve pull requests", under Workflow permissions, where the organization and its enterprise allow it: the template's weekly update of the protocol and its "Add a worker" form open their pull requests with GitHub's own token, which GitHub allows only with that box, and without it they answer with an issue or a link; the box lets a workflow approve a pull request too, which matters only where a ruleset requires a review, and the one this run applies requires none. The protocol alone brings neither workflow, so an existing repository's box is not touched. A ruleset of that name the repository has already is left as it is, and so is the topic. The pull request's section Settings says what was done and what GitHub refused, in GitHub's own words, and, where the organization's or the enterprise's policy forbids the box for GitHub Actions, who allows it and where; the next steps follow from it; the run's public log says only, per setting, whether it was done. Where no token for the repository can be made, the pull request says the App is not installed on it, or, when a probe on the owner's own installation fails too, that the front door's Setup App is not working; the run then tells the owner in an issue here, opened once and commented on after, since a red run would be reported only to the requester. A run that stops after the token was made says on the request that the settings may already be applied. The labels are made with the main App's token, as before; no variable is set and no secret is ever asked for: a Claude token is yours, set with /install-github-app in Claude Code. Then uninstall the Setup App: it holds Administration on your repository and nothing else uses it.

## What is shared, and how to turn it off

By default a repository that adopts the template shares anonymous aggregates of the protocol at work, so it can be measured in real projects: counts (claims, pull requests opened, merged and closed, reviews, changes requested, check runs passed and failed, conflicts, released claims, contributors as a number), how many people and Claude Code sessions were at work and the most at once, durations (medians and 90th percentiles from claim to pull request, from opening to merge, to the first review), rates (merge rate, first-check pass rate), the same pull requests counted again by how the work ran in parallel (with nothing beside it, one Claude Code session's several pull requests, one person's several sessions, several people, both at once, not known, the repository's own Claude workflows, other apps) and in pairs of pull requests at work at the same time, so that one person's several sessions are never pooled with several people's work, what the work cost (the tokens Claude used, by kind and by model family, what they would cost at Anthropic's API list prices and the seconds Claude was at work, beside the commits, failed checks and reverts of those pull requests), for the pull requests done alone and those done beside other work, with seven ratios between the two that say whether working in parallel did better, and, when a maintainer runs the judge, failure-type frequencies, in all and by the same settings. Never code, text, titles, logins, session links, file names, branch names or repository names: who opened each pull request, which Claude Code session made it and which files it changed are read in the run's memory to sort and count the pull requests, and are not written. Your repository's own workflow computes all of it but the failure-type frequencies and writes it to the file METRICS.json on its branch `metrics`; what Claude spent it reads from the line `Symphony-Usage:` that the template's Claude Code sessions add to their commits and from the usage records its Claude workflows keep, so in a repository that took the protocol alone, which brings neither, the tokens, their price and Claude's seconds stay at zero. Failure-type frequencies come only from JUDGE.json on that branch, which exists only when a maintainer runs the judge (`python3 tools/metrics.py judge`) on their own machine and their own Claude account, and which holds only counts of failure types, of the conversations judged and of those with two or more people, in all and by work setting, the totals of the failure types' three groups, the number of pull requests the run covered in each work setting, the days the run covered and any limit it ran under, the model's name, the prompt's version, when the file was made and the name of its schema. The App reads METRICS.json and JUDGE.json on the branch `metrics` and nothing else, and the dataset names your repository only by a salted hash. That workflow comes with the template; until the template carries it, an adoption records the switch and nothing is computed or shared. Everything the two Apps can read and write in a repository, what the developer receives and keeps, the full list of what METRICS.json holds among it, and how to stop each of those, is in PRIVACY.md here, also at https://openspineconsortium.com/symphony/apps-privacy.html, the page the Apps' descriptions on GitHub link.

To turn it off, at any time: choose "Do not share" in the form; or write `off` in `.github/symphony-metrics` on your default branch; or set the repository variable SDLC_METRICS to `off`. A repository adopted before the rename to Symphony keeps the metrics script it came with, which reads only `.github/sdlc-metrics`, the switch's name then: write `off` there. A later copy reads `.github/symphony-metrics`, and the old name only where that file is missing; one made from the template's release that reads both takes an off in either file. Uninstalling the App stops it too. While it is off, the workflow writes only that sharing is off.

## The template stays private

OpenSpineConsortium/symphony-template is internal to its enterprise, and adopting it does not change that. The App reads it inside this repository's workflow, with a read-only token that is revoked as soon as the files are read, and writes them into a pull request in your repository.

What that means: the files in the pull request are yours to read, change and keep, in a private repository or a public one, and nothing about them is hidden from you. What it does not mean: access to the template's repository itself, its history, its issues, its pull requests or its other branches, none of which leave the run; and no later change reaches your repository by itself. Later releases of the protocol come from the public OpenSpineConsortium/symphony-protocol, by its scripts/vendor.py and a pull request of your own, as the pull request's last lines say.

This repository is public, and so is everything on its issues: a repository name you type in the form, and the workflow run that handles it, are visible to anyone. If a private repository's name says more than you want to show, keep the issue's title a throwaway description, and come to the form from the install, which fills in the installation's number and no name: the run resolves the name for itself with the App's own token, masks it, and answers "your repository"; the number says nothing to anyone but the App. Until a request passes the run's checks, its log shows only whether the account you name has installed the App, and nothing about the repository itself: a repository the App does not reach and an author who is not one of its administrators get the same answer; a form carrying an installation that is not the App's, or one that reaches several repositories, or whose author is not an administrator of the one it reaches, gets one answer too. A request that passes shows what the run did there, as any run does, which is the name of your default branch, the labels it made and, per setting, whether the Setup App applied it; the files it staged, git's own messages, GitHub's answers about the settings, the names of your other branches and the number of any pull request or issue in your repository are never printed.

## How it works

- .github/ISSUE_TEMPLATE/adopt.yml, the form, labels its issue `adopt`: the installation GitHub fills in, or a repository's name, the kind (Auto by default), the merge choice (merge for me by default, or leave it open to review) and one box, do not share.
- .github/workflows/adopt.yml runs on that issue: it reads the form, makes the App's token for the account that owns your repository and checks with it, silently, that the App reaches the repository and that the issue's author is one of its administrators, or, when the form came from the install with the installation's number and no name, runs scripts/resolve.py, which turns either App's number into the newest repository the installation reaches with no adoption yet that the author administers and the Setup App is installed on, one per press, all by id; on both paths a repository without the Setup App is refused with its install link, except a named one adopted already, which gets the answer the run would give it; it answers what it refuses, and then calls adopt-run.yml with the repository's name, or with the ids, and answers an installation's request itself, unless the run refused the repository and so answered and closed the issue already.
- .github/workflows/adopt-run.yml is the adoption itself, for both of the form's paths: it makes the token that writes there, refuses a repository adopted already by the one rule (the Setup App then uninstalls itself, as after an adoption), reads the template with a read-only token, in mode existing fetches the protocol's page from the public OpenSpineConsortium/symphony-protocol at the release the template vendors, gives an empty repository its first commit, a README, then runs scripts/adopt.py on a checkout of your repository, commits on the branch symphony/adopt as the App, applies the settings with the Setup App's token where that App is installed and revokes it, opens the pull request, makes the labels and, in mode new, opens the setup issue; for a named repository it answers the issue too, and an installation's request is answered by adopt.yml, as above. Its header says why each step is as it is.
- scripts/jwt.sh signs an App's JWT with openssl, for the calls only an App's own JWT may make: reading its installations, minting an installation's token and, for the Setup App, asking which repositories its installation reaches. scripts/sweep.py, named for the sweep it once was, is the GitHub client and the adoption rules the two paths share: which of an installation's repositories have no adoption yet, and which kind a tree reads as.
- scripts/adopted.py asks, with the repository's token, whether it has an adoption already, by sweep.py's one check (docs/agents/PROTOCOL.md on the default branch), so a repository named on the form is judged as the installation's path judges it; it prints nothing that names the repository, and with `--answer` the one answer such a request gets.
- scripts/adopt.py does the reading and the copying: `parse` checks the form, `name` checks a repository's name once the run holds it, `apply` copies the files and writes a manifest of them, or refuses, before it writes anything, an adoption that could not write docs/agents/PROTOCOL.md, `body` writes the pull request's text from the manifest and the settings' report, `labels` reads the board's labels from the template's own list.
- scripts/setup.py applies the settings as the Setup App, through the REST API, and writes the report the pull request renders; `skip` writes the report that says why none was applied: no Setup App here, not installed on the repository, the front door's App broken, or a settings step that died before its report.
- scripts/refuse.sh answers a request that ends without a pull request: it says why on the issue and closes it.

## For the owner

One-time setup, by an owner of OpenSpineConsortium, before the form works. The label comes first: GitHub applies a form's label only when the label exists, and the workflow runs only on an issue that carries it, so a request opened before the label exists starts no run, is never answered and has to be opened again once the label is there. From then on, until the variable and the secret below are set, every request is answered that the front door is not set up yet, and stays open.

1. **Make the label the form applies**:

   ```bash
   gh label create adopt --repo OpenSpineConsortium/symphony-start --color 0e8a16 --description "A request for an adoption pull request, handled by .github/workflows/adopt.yml"
   ```

2. **Make the App public**, so accounts outside the organization can install it: https://github.com/organizations/OpenSpineConsortium/settings/apps/symphonyboard/advanced, "Make public".
3. **Give the App the permission Workflows: Read and write**: https://github.com/organizations/OpenSpineConsortium/settings/apps/symphonyboard/permissions, Repository permissions, Workflows. The pull request adds files under .github/workflows/, which GitHub lets an App write only with it. The run asks the App for a token with Contents, Pull requests, Issues and Workflows as Read and write, and Metadata as Read-only, for the one repository; the App has the first three already, and Workflows is new. Every existing installation, the organization's own included, then has to accept the new permission (the installation's page shows a review request) before it takes effect; a request for a repository whose installation has not accepted it is refused with a note that says so.
4. **Check the App's installation on OpenSpineConsortium includes symphony-template**: https://github.com/organizations/OpenSpineConsortium/settings/installations, Symphony, Configure, Repository access. "All repositories" is the right choice there: it covers the template, every test repository and every copy made later. An installation's list is one list, so opening the App's install link for another repository of the organization and choosing "Only select repositories" replaces the list rather than adding to it; the front door then fails at the template's token with "Not Found" until the template is back in the list. A repository of the organization's is added under Configure, never through the install link. The App need not be installed on this repository: every answer here is posted with the workflow's own token.
5. **Give this repository the App's id and private key**, as the variable SDLC_APP_ID (https://github.com/OpenSpineConsortium/symphony-start/settings/variables/actions) and the secret SDLC_APP_PRIVATE_KEY (https://github.com/OpenSpineConsortium/symphony-start/settings/secrets/actions). From a clone, with the key file the App's settings page generated; gh reads the key from the file and nothing prints it:

   ```bash
   gh variable set SDLC_APP_ID --repo OpenSpineConsortium/symphony-start --body 5258276
   gh secret set SDLC_APP_PRIVATE_KEY --repo OpenSpineConsortium/symphony-start < symphonyboard.private-key.pem
   ```

   Anyone who can push to this repository can reach that key through a workflow, so keep write access here to the organization's owners. A key that is set but wrong, or an id that is, gets every request the answer that the front door's App is not working, leaves the issue open and ends the run red, so that it is seen here.
6. **Protect main**: require a pull request and the check named "check" (.github/workflows/ci.yml), and block force pushes and deletions, at https://github.com/OpenSpineConsortium/symphony-start/settings/rules.
7. **Register the Setup App**, from a clone of OpenSpineConsortium/symphony-app, as an owner of the organization: `python3 scripts/register.py --setup --org OpenSpineConsortium`. Its manifest (manifest-setup.json there) gives it Administration and Metadata only, no webhook, and makes it public, so anyone can install it; the script writes its credentials to .sdlc-setup-app.env on your machine and prints the next step. GitHub gives it the slug symphony-setup unless the name was taken; if it gives another, change the install link in .github/ISSUE_TEMPLATE/adopt.yml, this README and tests/test_form.py (SETUP_APP_INSTALL). Then install the Setup App on this repository, OpenSpineConsortium/symphony-start, and only it ("Only select repositories"): the workflow asks that installation for a metadata-only token when a request's mint fails, which tells an adopter who did not install the App from a wrong id or key here. A test repository of the organization's is added to that list under Configure, as in step 4, since the install link's "Only select repositories" would replace it. Until this step and the next are done, every pull request says the front door has no Setup App yet, and the steps by hand stand.
8. **Give this repository the Setup App's id and private key**, as the variable SDLC_SETUP_APP_ID and the secret SDLC_SETUP_APP_PRIVATE_KEY, with the commands the script printed:

   ```bash
   gh variable set SDLC_SETUP_APP_ID --repo OpenSpineConsortium/symphony-start --body <its id>
   python3 scripts/register.py --env-file .sdlc-setup-app.env --print-key | gh secret set SDLC_SETUP_APP_PRIVATE_KEY --repo OpenSpineConsortium/symphony-start
   ```

   The same caution as in step 5 holds, more so: this key mints tokens with Administration on every repository whose owner installed the Setup App, for the length of a run, and only for a repository whose administrator asked. The workflow mints it after its checks, revokes it as soon as the settings are applied, and holds it on no repository of the organization's but this one, whose installation it asks for metadata alone. A key that is set but wrong, or an id that is, or the installation on this repository missing, is told from an adopter who did not install the App by that probe: the pull request says the front door's Setup App is not working, and the run opens the issue "Setup App of this front door is not working" here, or comments on it while it is open.

9. **Chain the installs**: on SymphonyBoard's settings page, under Post installation, set the Setup URL to Symphony Setup's install page, `https://github.com/apps/symphony-setup/installations/new`, and on Symphony Setup's set it to the form, `https://github.com/OpenSpineConsortium/symphony-start/issues/new?template=adopt.yml`; tick "Redirect on update" on both. GitHub then sends whoever installs SymphonyBoard on to Symphony Setup's install page, and whoever installs Symphony Setup, or adds a repository to its installation, to the form with `installation_id` in the query string, which fills in the form's Installation field (the Setup App's number, which the run resolves to the repository that installation reaches), so the person presses Create and the pull request is open within about two minutes; the state a link carried rides along to the form, and the run reads either App's number. Without this step the person finds the form through this README and names the repository there, or types the installation's number.

The files an adoption brings are offered under the MIT License, whose text is LICENSE here and which the pull request names. The adoption copies no LICENSE file into anyone's repository, since licensing your project is your decision.

## Checks

`bash scripts/check.sh` holds every file to ASCII with LF endings and a final newline and runs the tests on Python 3.12 (`PYTHON=python3 bash scripts/check.sh` takes another interpreter), and actionlint on the workflows when it is on PATH. CI runs the same script as the job named "check". The tests that run apply against the real template skip unless SDLC_TEMPLATE names a checkout of it, and CI here cannot read the template, so whoever can runs `SDLC_TEMPLATE=/path/to/symphony-template bash scripts/check.sh` before a change to scripts/adopt.py merges.
